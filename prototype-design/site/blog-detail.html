用不可变 revision 重写 CMS 的发布流程

草稿、审核与上线是三条线。把它们拆开之后，旧版本可以在新草稿审核期间继续在线，构建失败也不会把编辑状态拖下水。

周 周屿后端工程师 · 杭州

在最早的版本里，文章只有一张表、一个 status 字段：草稿、已发布、已下线。它很直观，直到我第一次想在不影响线上内容的情况下修改一篇已发布的文章。

一个字段承担了三件事

status = published 同时意味着「这是最新内容」「它被批准过」「访客能看到它」。只要我开始编辑，这三件事就不再同时成立。

  • 编辑中的内容不应该出现在线上；
  • 批准的是某个具体版本，而不是「这篇文章」；
  • 访客看到什么，取决于哪个站点版本已经构建成功并激活。

拆成三条线

于是每次保存都会生成一个不可变的 revision，文章本身只保存三个指针：

指针含义谁来改变它
current_revision当前编辑的版本保存 / 自动保存
desired_revision期望公开的版本发布、取消发布
live_revision当前线上的版本站点版本激活

保存时带上期望版本

并发编辑用乐观锁处理。客户端保存时带上它看到的版本号，服务端不一致就返回冲突，而不是悄悄覆盖：

PUT /api/v1/admin/posts/{id}
{
  "expected_revision_id": "01936f0e-7c1a-7b2e-9f0d-3c1a8e2b4d55",
  "title": "用不可变 revision 重写 CMS 的发布流程",
  "body_markdown": "..."
}
// 409 { "error": { "code": "revision_conflict" } }

审核绑定具体版本

提交审核锁定的是某个 revision。之后的编辑会产生新的 revision，不会继承旧版本的批准。

上线是另一件事

「发布」只是把一个已批准的 revision 设为期望公开版本，然后排队构建。只有构建成功、新的 generation 被激活，访客才看得到。构建失败时，上一个线上版本保持不变。

发布不是上线。把这两个词分开，后台的状态文案就不会骗人。

小结

三条线让每个状态都有唯一的来源。代价是表和接口多了一些，换来的是：旧版本永远不会被新草稿覆盖，也不会因为一次失败的构建而消失。
