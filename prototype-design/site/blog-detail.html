基于 GitHub Actions 与 Docker 的 Go 项目部署实战

对于 Go 项目，怎样搭一套既简单可靠、又方便回滚的部署流程？这篇从多阶段构建讲到镜像推送、远程部署和一键回滚。

在现代软件开发中，自动化部署已经是提升团队效率和产品质量的关键环节。对 Go 开发者来说，静态编译让部署天然简单，但「简单」不等于「可靠」：镜像怎么打得小、密钥放在哪、出了问题怎么回滚，都需要提前想清楚。

一、整体流程

整条流水线分为四步：代码检查与测试、构建镜像、推送到镜像仓库、通过 SSH 在服务器上拉取并重启。每一步失败都会中止后续步骤，线上保持上一个版本。

阶段触发条件产物失败时
test每次 push测试报告中止
buildmain 分支镜像 app:sha中止
deploy打 tag线上容器保留旧版本

二、多阶段构建

Go 程序编译后只有一个二进制文件，运行阶段不需要工具链。用多阶段构建，最终镜像可以从近 1GB 降到二十几 MB。

FROM golang:1.23-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app ./cmd/server

FROM gcr.io/distroless/static
COPY --from=build /app /app
ENTRYPOINT ["/app"]

缓存依赖层

先复制 go.mod 和 go.sum 再下载依赖，只要依赖没变，这一层就会命中缓存，构建时间能省下一大半。

三、GitHub Actions 工作流

on:
  push:
    tags: ['v*']
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/clin211/app:${{ github.ref_name }}
密钥一律放在仓库的 Secrets 里，工作流只通过环境变量读取，不要写进镜像，也不要打印到日志。

四、回滚

每次部署都用 tag 作为镜像版本，回滚就是把服务指回上一个 tag：

  • 服务器上保留最近 5 个镜像版本；
  • 部署脚本记录当前版本到文件，方便一键切回；
  • 健康检查失败时自动回退，并在 Actions 里标红。

小结

这套流程没有用到任何复杂的编排工具，但覆盖了日常最需要的三件事：构建可复现、密钥不外泄、出了问题能马上回去。等服务多起来，再考虑引入更完整的平台也不迟。
